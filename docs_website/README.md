# docs_website — the docs portal (VitePress)

This directory holds **only the site tooling** for the rendered documentation portal. The actual
documentation content lives in the sibling [`../docs/`](../docs/) directory (`arc42/`, `adr/`,
`domain/`, `services/`, …) and is intentionally kept content-only, because the project's Claude Code
skills and agents reference those `docs/<…>` paths directly.

VitePress renders `../docs` via `srcDir` in `.vitepress/config.mts`. The sidebar is generated by
scanning that tree, so every new Markdown file shows up automatically.

## Run it

```bash
cd docs_website
npm install           # also creates the ../docs/node_modules symlink via postinstall (see below)
npm run docs:dev      # local dev server
npm run docs:build    # production build -> .vitepress/dist
npm run docs:preview  # preview the build
npm run docs:check    # parse every Mermaid diagram under ../docs
```

## Configure

Open `.vitepress/config.mts` and adjust:

- `BASE` — the path the site is served under (`/<slug>/` for a GitHub Pages project site, or `/`).
- `REPO_URL` — set the GitHub owner so "Edit this page" and the social link point at your repo.
- `title` / `siteTitle` / `description` / `footer` — site metadata.

## Why the `docs/node_modules` symlink

VitePress resolves each Markdown page's runtime deps (e.g. `vue/server-renderer`) from the page's own
location. Because the pages live in `../docs` (a sibling of this app, not a subfolder), that directory
needs a `node_modules` on its resolution path. Rather than install a second copy, the `postinstall`
script (`scripts/link-content-node-modules.mjs`) symlinks `../docs/node_modules` → this app's
`node_modules`. The symlink is gitignored and recreated on every `npm install`.
